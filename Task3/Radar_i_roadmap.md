# Задание 3. Технологический радар и роадмап изменений

**Компания:** «Будущее 2.0» (медицинские услуги + финтех, банковская лицензия)
**Цель:** сформировать технологический радар и роадмап изменений, привязанный к бизнес-целям компании

---

## 1. Технологический радар

Диаграмма радара представлена в файле `Tech_Radar.drawio.xml`. Кольца радара:

- **ADOPT** — технологии, которые внедряем в производство (новые и существующие);
- **TRIAL** — технологии в пилотных проектах;
- **ASSESS** — технологии, которые оцениваем;
- **HOLD** — технологии, которые выводим из эксплуатации или заменяем.

### Связь технологий с бизнес-сценариями

| Технология | Статус | Поддерживаемые бизнес-сценарии |
|---|---|---|
| **Yandex Cloud (IaaS)** | ADOPT | Масштабирование ресурсов для работы с данными; отказоустойчивость, резервное копирование, геораспределённое развёртывание; снижение затрат на поддержку устаревшего оборудования |
| **Kubernetes** | ADOPT | Оркестрация контейнеров; независимые среды доменов; быстрое масштабирование сервисов |
| **Kafka (событийная шина)** | ADOPT | Интеграция новых бизнесов (фармацевтика, электроника) без изменений в DWH; обмен событиями между доменами |
| **ClickHouse** | ADOPT | Быстрая подготовка отчётности: сложные отчёты за минуты вместо часов |
| **PostgreSQL** | ADOPT | Хранилища доменов (медицинские, финансовые, обезличенные данные) с шифрованием TDE |
| **Airflow** | ADOPT | Оркестрация ETL/ELT-задач; автоматизация загрузки данных в витрину |
| **Keycloak (IAM)** | ADOPT | Уровни доступа сотрудников к витрине данных; соответствие требованиям регуляторов |
| **API Gateway (Kong)** | ADOPT | Единая точка интеграции для партнёров; контроль доступа и трафика |
| **Terraform (IaC)** | ADOPT | Воспроизводимость и масштабируемость инфраструктуры; автоматизация развёртывания |
| **Object Storage (S3)** | ADOPT | Хранение больших объёмов данных (сотни терабайт) с шифрованием |
| **Data Mesh (методология)** | ADOPT | Децентрализованное владение данными; подключение новых доменов без изменений в DWH |
| **Стеки доменов: Python / Golang / Java** | ADOPT | Существующие стеки ИИ-сервисов (Python) и финтех-сервисов (Golang/Java) сохраняются и развиваются |
| **dbt (ELT-трансформации)** | TRIAL | Пилот: трансформации данных в аналитическом хранилище |
| **Data Catalog (DataHub)** | TRIAL | Пилот: каталог данных, владельцы, качество |
| **Superset (BI)** | TRIAL | Пилот: замена кастомизаций Power BI |
| **Apache Spark** | TRIAL | Пилот: обработка больших объёмов данных (сотни терабайт) |
| **MLflow (MLOps)** | ASSESS | Оценка: управление жизненным циклом моделей ИИ |
| **Apache Flink** | ASSESS | Оценка: потоковая обработка событий |
| **SQL Server 2008 (DWH)** | HOLD | Выводится: неподдерживаемая СУБД, заменяется хранилищами доменов |
| **PowerBuilder** | HOLD | Выводится: заменяется веб-интерфейсом МИС |
| **Apache Camel (ESB)** | HOLD | Заменяется событийной шиной Kafka |
| **Power BI (кастомизации)** | HOLD | Заменяется BI-платформой поверх витрины данных |

## 2. Роадмап изменений

Роадмап привязан к целям бизнеса: промежуточное состояние (через пару месяцев) и финальное состояние (через год).

### Этап 0. Архитектурное решение (0–2 месяца)

| Параметр | Значение |
|---|---|
| **Действия** | Согласование целевой архитектуры; определение границ доменов; описание ключевых связей; выбор облачного провайдера; создание платформенной команды; планирование проектов по витрине данных в доменах |
| **Ожидаемые результаты** | Согласованное архитектурное решение; карта доменов и связей; план проектов по витрине данных |
| **Ответственные команды** | Архитектурный комитет, платформенная команда, руководители подразделений |
| **Необходимые ресурсы** | Архитекторы, аналитики, бюджет на облачную инфраструктуру |
| **Обоснование** | Без согласованной архитектуры и границ доменов дальнейшие изменения будут хаотичными. Этап соответствует промежуточной цели бизнеса: «архитектурное решение сформировано и согласовано» |

### Этап 1. Облачная платформа и инфраструктура (2–4 месяца)

| Параметр | Значение |
|---|---|
| **Действия** | Развёртывание облачной инфраструктуры (IaaS) через Terraform; настройка Kubernetes; сети, NAT, безопасность; резервное копирование |
| **Ожидаемые результаты** | Облачная среда с отдельными пространствами для доменов; IaC-конфигурации; базовые механизмы отказоустойчивости |
| **Ответственные команды** | Платформенная команда, DevOps |
| **Необходимые ресурсы** | DevOps-инженеры, бюджет на облако, Terraform |
| **Обоснование** | Облако позволяет быстрее масштабировать ресурсы для работы с данными и сокращает затраты на поддержку устаревшего оборудования. IaC обеспечивает воспроизводимость сред |

### Этап 2. Событийная шина и интеграционный слой (4–6 месяцев)

| Параметр | Значение |
|---|---|
| **Действия** | Развёртывание Kafka; API Gateway; миграция интеграций с ESB (Apache Camel) на событийную шину; подключение доменов к шине |
| **Ожидаемые результаты** | Событийная шина в проде; домены публикуют события; ESB выводится |
| **Ответственные команды** | Платформенная команда, интеграционная команда |
| **Необходимые ресурсы** | Инженеры интеграции, Kafka-кластер |
| **Обоснование** | Событийная шина — основа для подключения новых бизнесов без изменений в DWH. Устраняет узкое место ESB (проблема П-05) |

### Этап 3. Разделение доменов и вынос бизнес-логики из DWH (4–8 месяцев)

| Параметр | Значение |
|---|---|
| **Действия** | Домен «Финтех»: вынос бизнес-логики из DWH в сервисы, собственное хранилище. Домен «ИИ-сервисы»: ETL с обезличиванием, собственное хранилище. Домен «Клиники»: веб-интерфейс МИС вместо PowerBuilder, миграция данных из DWH |
| **Ожидаемые результаты** | Независимые домены с собственными хранилищами; бизнес-логика вынесена из DWH; PowerBuilder выведен |
| **Ответственные команды** | Команды доменов (финтех, ИИ, клиники) |
| **Необходимые ресурсы** | Разработчики (Golang/Java, Python, Java/Spring), DBA, специалисты по обезличиванию |
| **Обоснование** | Вынос бизнес-логики из DWH (проблема П-02) и разделение на домены (П-07) — ключевое условие независимого развития направлений и подключения новых бизнесов |

### Этап 4. Аналитическое хранилище и витрина данных (6–10 месяцев)

| Параметр | Значение |
|---|---|
| **Действия** | Развёртывание ClickHouse; ETL/ELT (Airflow, dbt); разработка витрины данных — портала самообслуживания; BI-платформа; интеграция с Keycloak (уровни доступа) |
| **Ожидаемые результаты** | MVP витрины данных: отчёты по срезам, конструктор отчётов; BI-дашборды |
| **Ответственные команды** | Команда данных, BI-команда, платформенная команда |
| **Необходимые ресурсы** | Инженеры данных, BI-разработчики, ClickHouse, Airflow |
| **Обоснование** | Витрина данных — ключевой результат года. Устраняет проблему медленной отчётности (П-01) и отсутствия самообслуживания (П-06). Медицинские данные в витрину не включаются — только обезличенные |

### Этап 5. Запуск витрины данных и подключение партнёров (10–12 месяцев)

| Параметр | Значение |
|---|---|
| **Действия** | Запуск портала самообслуживания для бизнес-пользователей; подключение фармацевтических компаний и производителя электроники как новых доменов; обучение пользователей |
| **Ожидаемые результаты** | Реализованный портал самообслуживания; бизнес-пользователи в доменах работают с данными в рамках новой архитектуры; партнёры подключены |
| **Ответственные команды** | Все команды доменов, платформенная команда |
| **Необходимые ресурсы** | Поддержка пользователей, документация, обучение |
| **Обоснование** | Соответствует финальной цели бизнеса: «реализован портал самообслуживания, бизнес-пользователи работают с данными». Допускается временное сохранение легаси-систем в отдельных доменах |

### Этап 6. Качество медицинских и финансовых сервисов (постоянно)

| Параметр | Значение |
|---|---|
| **Действия** | Мониторинг и алертинг; резервное копирование и восстановление; геораспределённое развёртывание критичных систем; аудит безопасности; соответствие требованиям регуляторов (152-ФЗ, ЦБ РФ) |
| **Ожидаемые результаты** | Высокая доступность сервисов; соответствие регуляторным требованиям; защита медицинских и финансовых данных |
| **Ответственные команды** | Платформенная команда, команда безопасности, комплаенс |
| **Необходимые ресурсы** | SRE-инженеры, специалисты по ИБ, инструменты мониторинга |
| **Обоснование** | Меры критически важны для поддержания качества медицинских и финансовых сервисов и доверия клиентов |

## 3. Обоснование планируемых изменений

| Этап | Влияние на бизнес |
|---|---|
| **Этап 0** (архитектурное решение) | Согласованная архитектура — фундамент всех изменений; снижает риски хаотичных инвестиций |
| **Этап 1** (облачная платформа) | **Снижение затрат**: отказ от поддержки устаревшего оборудования; **масштабирование**: быстрый рост ресурсов под данные; **надёжность**: отказоустойчивость и резервное копирование |
| **Этап 2** (событийная шина) | **Скорость выхода на рынок**: подключение новых сервисов и партнёров за дни вместо месяцев; **масштабирование**: новые бизнесы без изменений в DWH |
| **Этап 3** (разделение доменов) | **Скорость принятия решений**: команды развивают направления независимо; **качество сервисов**: изоляция медицинских и финансовых данных, соответствие регуляторам |
| **Этап 4** (витрина данных) | **Скорость принятия решений**: отчёты за минуты вместо часов; **самообслуживание**: сотрудники не зависят от ИТ |
| **Этап 5** (запуск и партнёры) | **Выручка**: новые бизнес-направления (фармацевтика, электроника) подключаются к экосистеме; **масштабирование**: целостное представление по ключевым показателям |
| **Этап 6** (качество сервисов) | **Качество**: высокая доступность медицинских и финансовых сервисов; **доверие**: соответствие требованиям регуляторов и защита данных |

**Итог.** Роадмап обеспечивает поэтапный переход от монолитного DWH к облачной архитектуре с независимыми доменами и витриной данных — порталом самообслуживания. Каждый этап привязан к бизнес-целям компании: скорость принятия решений, качество сервисов, снижение затрат и масштабирование для новых бизнесов.
