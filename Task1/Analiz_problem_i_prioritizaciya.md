# Задание 1. Проектирование целевой архитектуры и приоритизация проблем

**Компания:** «Будущее 2.0» (медицинские услуги + финтех, банковская лицензия)
**Цель:** целевая архитектура через год, поддерживающая ключевые бизнес-сценарии компании

---

## 1. Целевая архитектура (C4-диаграмма контейнеров)

Диаграмма контейнеров представлена в файле `C4_Containers_ToBe.drawio.xml` (модель C4, уровень контейнеров).

### Ключевые решения целевой архитектуры

| Решение | Как поддерживает бизнес-сценарии |
|---|---|
| **Отдельные облачные среды доменов** (Клиники, Финтех, ИИ-сервисы, Головной офис) | Независимое развитие направлений: команды финтеха и ИИ не блокируют друг друга, релизы не зависят от общего DWH |
| **Витрина данных — портал самообслуживания** | Быстрая подготовка отчётности: сотрудник сам строит отчёты по любым срезам в пределах уровня доступа, без заявок в ИТ |
| **Аналитическое хранилище (ClickHouse)** | Отчёты за минуты вместо часов: колоночное хранилище оптимизировано под аналитические запросы |
| **Событийная шина (Kafka) вместо ESB** | Масштабирование для новых бизнесов: фармацевтика и электроника подключаются через события, без изменений в DWH |
| **API Gateway** | Единая точка интеграции для партнёров, контроль доступа и трафика |
| **Каталог данных + оркестратор (Airflow)** | Управляемость: владельцы данных, метаданные, качество, автоматизация ETL |
| **IAM / Keycloak** | Уровни доступа сотрудников к витрине данных, соответствие требованиям регуляторов |
| **Обезличивание медицинских данных** | Медицинские карты, истории болезней и результаты исследований **не включаются в витрину данных** — в аналитику попадают только обезличенные данные |
| **Легаси-системы (DWH, PowerBuilder) — временное сохранение** | Поэтапная миграция без остановки бизнеса; данные переносятся в новые хранилища доменов |

### Как целевая архитектура поддерживает ключевые бизнес-сценарии

1. **Быстрая подготовка отчётности.** Сотрудник через витрину данных (портал самообслуживания) получает отчёт по любым необходимым срезам в пределах своего уровня доступа и конструирует собственные отчёты. Данные хранятся в аналитическом хранилище ClickHouse, оптимизированном под аналитические запросы, — сложные отчёты строятся за минуты вместо часов.

2. **Независимое развитие финтех- и ИИ-направлений.** Каждый домен разворачивается в отдельной облачной среде со своими сервисами и хранилищами. Бизнес-логика вынесена из DWH в сервисы доменов. Команды финтеха (Golang/Java) и ИИ (Python) развивают свои продукты независимо.

3. **Масштабирование для новых бизнесов.** Новые направления (фармацевтика, электроника) подключаются через событийную шину и API Gateway как новые домены — без внесения бизнес-логики в DWH. Подход Data Mesh: каждый домен владеет своими данными и публикует их как продукты.

4. **Качество медицинских и финансовых сервисов.** Медицинские данные защищены и не используются в аналитике (только обезличенные). Финансовые данные изолированы в домене финтеха. Соответствие требованиям регуляторов (ЦБ РФ, Росздравнадзор) обеспечивается уровнями доступа и аудитом.

## 2. Проблемные места

| № | Проблема | Описание | Какие бизнес-сценарии страдают |
|---|---|---|---|
| П-01 | **Медленная подготовка отчётности** | Сложные отчёты строятся часами: сотни терабайт данных, множество трансформаций, DWH на SQL Server 2008 не справляется с нагрузкой | Задержки в принятии управленческих решений; замедление time-to-market аналитики |
| П-02 | **Бизнес-логика в DWH** | Значительная часть бизнес-логики реализована внутри DWH (хранимые процедуры, триггеры) | Невозможность независимого развития направлений; любое изменение логики затрагивает всех |
| П-03 | **Устаревший стек: SQL Server 2008** | СУБД 2008 года не поддерживается производителем, нет обновлений безопасности | Риски информационной безопасности; невозможность соответствия требованиям регуляторов; ограничения производительности |
| П-04 | **Устаревший клиент PowerBuilder** | Интерфейс операторов на PowerBuilder, сложно развивать, нет современных возможностей | Снижение качества медицинских сервисов; высокая стоимость поддержки |
| П-05 | **ESB (Apache Camel) — узкое место интеграции** | Все интеграции проходят через старую шину данных, она не масштабируется | Замедление подключения новых сервисов и партнёров; риск отказа единой точки |
| П-06 | **Нет самообслуживания в отчётности** | Отчёты заказываются через ИТ-специалистов, BI с большим количеством кастомизаций поверх DWH | Задержки получения отчётности; нагрузка на ИТ; невозможность быстрых срезов |
| П-07 | **Отсутствие разделения на домены** | Клиники, финтех и ИИ-сервисы работают с общим DWH, данные перемешаны | Невозможность независимого развития; сложность контроля доступа; риски утечки данных между направлениями |
| П-08 | **Ограниченная масштабируемость on-premise** | Объём данных измеряется сотнями терабайт и растёт, on-premise инфраструктура не масштабируется быстро | Замедление аналитических процессов; невозможность быстрого подключения новых бизнесов |
| П-09 | **Смешение медицинских и финансовых данных** | Медицинские и финансовые данные хранятся в одном DWH без чёткого разграничения | Риски нарушения требований регуляторов (152-ФЗ, требования ЦБ РФ); сложность аудита доступа |
| П-10 | **Отсутствие целостного представления по ключевым показателям** | При развитии направлений отдельно нет единой картины по ключевым бизнес-показателям | Затруднено стратегическое управление компанией |

## 3. Приоритизация проблем

### 3.1. Метод MoSCoW

| Приоритет | Проблемы | Связь с целями бизнеса |
|---|---|---|
| **Must have** (критично) | П-01 (медленная отчётность), П-02 (бизнес-логика в DWH), П-03 (SQL Server 2008) | Блокируют выручку и скорость принятия решений; создают регуляторные и безопасностные риски; без их решения невозможно независимое развитие направлений |
| **Should have** (важно) | П-05 (ESB — узкое место), П-06 (нет самообслуживания), П-07 (нет доменов) | Замедляют time-to-market и подключение новых бизнесов; без них не запустится витрина данных |
| **Could have** (желательно) | П-04 (PowerBuilder), П-08 (масштабируемость), П-10 (целостное представление) | Улучшают качество сервисов и управляемость, но допустимо отложить на поздние этапы |
| **Won't have** (сейчас) | П-09 (полное разграничение всех данных) | Полное разграничение всех данных — долгосрочная задача; на первом этапе достаточно изоляции доменов и обезличивания |

### 3.2. Матрица Эйзенхауэра

| | **Срочно** | **Не срочно** |
|---|---|---|
| **Важно** | **П-01** — медленная отчётность (часы) блокирует управленческие решения<br>**П-03** — SQL Server 2008 без поддержки = риск безопасности и регуляторики | **П-02** — вынос бизнес-логики из DWH<br>**П-07** — разделение на домены |
| **Не важно** | **П-05** — ESB как узкое место (решается вместе с переходом на событийную шину) | **П-04** — замена PowerBuilder<br>**П-08** — масштабируемость<br>**П-10** — целостное представление |

## 4. Выводы

Приоритизация связана с целями бизнеса:

1. **Критично для выручки и скорости принятия решений** (Must have, важно и срочно): устранение медленной отчётности (П-01) и вывод из эксплуатации неподдерживаемого SQL Server 2008 (П-03). Эти проблемы напрямую замедляют принятие управленческих решений и создают регуляторные риски.

2. **Критично для независимого развития направлений** (Must have, важно, не срочно): вынос бизнес-логики из DWH (П-02) и разделение на домены (П-07). Без этого финтех и ИИ-направления не смогут развиваться независимо, а новые бизнесы (фармацевтика, электроника) не будут подключаться без изменений в DWH.

3. **Критично для запуска витрины данных** (Should have): замена ESB на событийную шину (П-05) и внедрение самообслуживания (П-06). Витрина данных — портал самообслуживания — является ключевым результатом года и опирается на эти изменения.

4. **Улучшение качества сервисов** (Could have): замена PowerBuilder (П-04) повышает качество медицинских сервисов, но допустима на поздних этапах при временном сохранении легаси.

Таким образом, целевая архитектура (диаграмма контейнеров) и приоритизация проблем образуют единое решение: сначала устраняются критические ограничения (отчётность, безопасность, монолит DWH), затем создаётся платформа для независимого развития доменов и запускается витрина данных.
